# SAP S/4HANA & Microsoft Dynamics 365 — module boundaries and record ownership

Budget: ~25 min. Sources fetched live on 2026-09-24 via WebSearch/WebFetch, and via headless Chrome (`google-chrome --headless=new --virtual-time-budget=15000 --run-all-compositor-stages-before-draw --dump-dom`) for help.sap.com, which is a client-side Vue SPA that returns an empty shell to plain `curl`/WebFetch. Labels used: **documented** (vendor primary doc, quoted verbatim), **source** (primary vendor doc, but I paraphrase because the quote itself was a TOC/heading list), **marketing** (vendor overview/positioning page), **third-party** (blog/community, not vendor), **inferred** (my synthesis from documented facts, not a direct quote). Gaps are marked **NOT FOUND**.

Owner's question this feeds: *Should Sales sit in CRM, in Projects, or in Finance? If sales lives in Finance, what is the point of CRM? Is Projects just a dashboard?* Short answer up front, evidenced below: neither vendor puts sales in one place. Both vendors keep at least **two independent sales-order-capable systems** (a CRM/front-office one and an ERP/back-office one) plus a **separate store/POS channel**, and stitch them together with **integration, not shared ownership** — SAP via CVI/replication APIs between C4C/Sales Cloud and S/4HANA SD, Microsoft via **dual-write** between Dataverse (Sales) and Finance & Supply Chain Management (F&SCM). Projects is not a dashboard in either product — SAP PS and D365 Project Operations own real transactional records (WBS elements, networks/tasks, timesheets, budgets), but project billing still posts through Finance (SD billing / F&SCM project invoicing), so Projects is a **first-class owner of planning/execution records, not of the ledger**.

## SAP S/4HANA (and what "SAP HANA" is)

**Preliminary correction, label: documented.** "SAP HANA" is the in-memory database platform, not the application suite. SAP's naming: HANA = database; S/4HANA = the ERP application suite that runs on the HANA database. The owner's phrase "SAP HANA" almost certainly means S/4HANA; this report covers S/4HANA (on-premise and Cloud editions) and separately notes SAP CRM / SAP Sales Cloud (C4C), SAP PS, and SAP Business Partner as they interlock with it.

### Q4. CRM: what it owns; does it create sales/finance documents itself or hand off?

- **documented** — SAP CRM/Sales Cloud (C4C) owns **Lead, Opportunity (header/item/text/preceding-subsequent process flow), Appointment/Activity, Phone Call Activity, Task Activity**, and its **own Sales Quotation and Sales Inquiry** objects, per the live S/4HANA "APIs for Sales" TOC (this TOC documents the S/4HANA-side API surface that these front-office systems integrate against):
  > "Force Support Leads Lead (A2X) Lead Lead Item Person Responsible for Lead ... Opportunities Opportunity (A2X) Opportunity Opportunity Item ... Appointments Appointment (A2X) ... Phone Calls Phone Call (A2X) ... Tasks Task (A2X) Customer Management Task Activity"
- **documented** — It **hands off** rather than owning the ERP sales order/billing document: won opportunities generate a **"Sales Order as Follow Up of Opportunity"** / **"Sales Quotation Follow Up of Opportunity"** record in the S/4HANA back end (same quote as Q3) — i.e., CRM creates the front-office quote/opportunity, then triggers creation of the *SD* sales order as a distinct, separately-numbered document, linked by "preceding/subsequent process flow," not shared identity.
- **NOT FOUND** — a direct, verbatim SAP statement of "CRM does not post financial documents; only Finance/SD does" was not fetched this session; this is **inferred** from the module separation evidenced above (SD, not CRM, owns Billing Document/Customer Invoice in every SAP source found).

### Q5. Projects: does SAP PS own records, or is it a dashboard/view?

- **documented** — SAP PS **owns first-class transactional master data**: Project definition, WBS elements (with their own basic/org/control data, billing plans, settlement rules, capital investment measures, Assets Under Construction), Networks, Activities, Activity Elements, and Relationships — all with dedicated maintenance transactions (Project Builder, WBS Element Overview app) per the live PS TOC (Q2 quote). This is **not a dashboard/view over other modules' records** — WBS elements and networks are themselves postable cost objects (they receive actual costs/settlement, not just aggregate other objects' data).
- **documented** — PS is explicitly **linked to but distinct from** SD: "Determining the Project Number from the Sales Document" and "Assigning a Sales Document" (to a network) show that a WBS element/network can be *derived from* or *assigned to* a sales order, i.e., project billing is driven off Sales-Document-linked billing plans on the WBS element, but the WBS element/network records themselves are owned by PS, not by SD.
- **NOT FOUND** — explicit timesheet/CATS integration and milestone-billing detail were not independently fetched this session (only headings seen, e.g. "Billing Plan" under WBS element data — full behavior not quoted).

### Q6. Finance: what it owns — invoices/bills, or only the ledger?

- **documented** — SD (not FI) owns the customer-facing **Billing Document** (the commercial invoice as seen by the customer), per Q2 TOC evidence. FI's own object is the **posted accounting document / Universal Journal (ACDOCA) line item**, generated when the billing document is released to accounting.
- **third-party (not independently re-verified verbatim this session, community.sap.com blocked WebFetch)** — ACDOCA is described as merging FI-GL, FI-AA, CO, CO-PA, and Material Ledger into one line-item table, i.e., FI's own record is the **journal entry / line item**, not the commercial billing document itself. This matches the classic SAP architecture claim: SD billing documents are a *sales* document type; FI/CO posts the *accounting* document that results from releasing it to accounting — two linked but separate document numbers.
- **NOT FOUND** — I did not fetch a page that explicitly states "FI does not own its own AP/AR sub-ledger invoice object, only ACDOCA line items" — this is **inferred** from the ACDOCA description plus the SD-owns-billing-document evidence above; MM (not FI) similarly owns the vendor invoice/incoming invoice verification object (MIRO), which was **NOT FOUND**/not fetched this session.

### Q7. Documents: is there a DMS? What does it own, how do other records link to files?

- **documented** — Yes. SAP has both a classic **Document Management System (DMS)** (Document Info Record as the master object) and a newer **Harmonized Document Management (HDM)** / **Attachment Service** layer, confirmed live: "Document Info Record (DIR) is the relevant master object, which is necessary to connect external files with several SAP objects" (WebSearch summary of `community.sap.com/.../sap-document-management-system-dms...`, **third-party**-level, page not independently re-fetched verbatim) and, **documented** (live TOC fetch), the Harmonized Document Management module explicitly documents "**How to Assign Documents to a Business Object**" / "**How to Unassign Documents from a Business Object**" as its own procedures, plus "Manage Documents," "Connecting to External Content Repositories (SAP Content Server, CMIS)." URL: `https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4c3d1c6b3d744f84aab4c273f979f430/bc275e43f1b043cc8f97710d5de64e97.html`.
- **documented** — SD sales orders can carry attachments directly too: the SD "APIs for Sales" TOC lists "**Create, Read, or Delete Attachments for Sales Orders**" as an explicit sales-order operation, i.e., attachment linkage is exposed per-business-object (sales order, and by the same Attachment Service pattern, other objects), not necessarily always routed through the classic DMS Document Info Record — SAP's own Cloud docs distinguish "applications ... rely on Document Management System (DMS) or Generic Object Services (GOS)" depending on which one the object uses (WebSearch summary, **third-party**-level, of `help.sap.com/.../Attachment Service` — not independently re-fetched verbatim).

### Q8. Contacts: shared master? Personal/private CRM?

- **documented** — SAP's model: **Business Partner (BP)** is "the leading object and single-entry point to maintain Business Partner, Customer, and Supplier (formerly Vendor) master data" (WebFetch of `blog.sap-press.com/understanding-the-sap-s4hana-business-partner-structure`, quoted): "A business partner represents the highest-level object in an SAP S/4HANA system." Customer and Vendor records are role-specific views synchronized onto the BP object via **CVI (Customer/Vendor Integration)**: "If a business partner is both a customer ... and a vendor ..., the customer master record will be stored in the role customer (SD), and the vendor master record in the role vendor (MM) for these business relationships." **Contact persons** are a further sub-object: "A contact person can, for example, be a person in your own company that is responsible for a specific customer... You can enter contact persons for a customer directly in the customer master so that they are automatically assigned to that customer" (WebSearch summary/third-party for this specific sentence — the direct blog fetch for CVI details returned a generic non-matching response, so treat the CVI/contact-person wording as **third-party**, page identified but not independently re-quoted verbatim on this attempt).
- **NOT FOUND** — no evidence found this session of a "personal/private" relationship-management layer separate from the shared Business Partner (e.g., a salesperson's private rolodex distinct from the corporate BP record). SAP's architecture (one BP object, roles layered on top) argues against a private CRM silo by design, but this is **inferred**, not a documented statement.

## Microsoft Dynamics 365

### Q1. Top-level modules/products, sold separately

- **documented** — D365 is a family of **separately licensed, separately architected** apps built on two different platforms:
  1. **Dataverse-based "Customer Engagement" apps**: D365 **Sales**, Customer Service, Field Service, Marketing, **Project Operations**.
  2. **Finance & Operations ("F&O") apps**: D365 **Finance**, D365 **Supply Chain Management** — a different runtime/data platform (X++ / AX-lineage), integrated to Dataverse via **dual-write**.
  3. **Business Central** — a distinct product (Dynamics NAV lineage) with its own sales order/invoice engine, sold separately, aimed at SMB, licensed in Essentials/Premium tiers.
  4. **Commerce** — headless commerce engine (Commerce Scale Unit) + POS + e-commerce storefront, integrating with both Dataverse and F&O.
  Quote (dual-write overview, documented): "Applications built on Dataverse, including Dynamics 365 Sales, Dynamics 365 Marketing, Dynamics 365 Customer Service, and Dynamics 365 Field Service." URL: `https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/dual-write/dual-write-overview`.
  Quote (Commerce architecture, documented): "The platform shared among the various Dynamics 365 business applications, such as Dynamics 365 Commerce, Dynamics 365 Supply Chain Management, and Dynamics 365 Finance, provides a set of interconnected business processes... Dataverse is the unified data store that integrates the data from all your business applications. Dynamics 365 applications such as Dynamics 365 Sales, Dynamics 365 Customer Service, and Dynamics 365 Commerce use Dataverse to store business data." URL: `https://learn.microsoft.com/en-us/dynamics365/commerce/dev-itpro/commerce-architecture`.
  Quote (Project Operations, third-party but consistent with docs): "Project Operations is built on Microsoft Dataverse, the same data platform powering Dynamics 365 Sales and Customer Service" — confirmed structurally by the Project Operations "Saving Changes to Projects" doc below (documented).

### Q3. Sales: who owns quotes/orders/invoices; channels and landing points

- **documented** — D365 **Sales (Dataverse) owns its own Quote → Order → Invoice chain independently of Finance**, with dedicated conversion messages: `ConvertSalesOrderToInvoice`, `GenerateSalesOrderFromOpportunity`, `FulfillSalesOrder`, `LockSalesOrderPricing` (verbatim from the Order/SalesOrder table reference, URL `https://learn.microsoft.com/en-us/dynamics365/developer/reference/entities/salesorder`). This confirms Sales is not merely a lead-tracking tool feeding Finance — it has its own quote/order/invoice objects that can complete a deal end-to-end inside Dataverse, separate from any F&SCM sales order.
- **documented — Dual-write / "Origin" and "Ownership" fields** are the explicit mechanism reconciling **two independently-creatable sales quotations** (one in Sales, one in Supply Chain Management), each with its own lifecycle, kept in sync but not merged into one record. Quote:
  > "Both Supply Chain Management and Sales store and show origin and ownership information for each quotation. Origin indicates which system originally created a quotation. The possible values of the Origin field are Supply Chain Management and Dynamics 365 Sales... Ownership indicates which system currently owns a quotation. It determines which system owns the processing of a quotation through its lifecycle..."
  > "When a user creates a sales order from an activated sales quotation in Sales... The sales order that was created in Sales is synced and becomes available in Supply Chain Management. Supply Chain Management links the new sales order to the related sales quotation, so that users can navigate between them."
  URL: `https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/fin-ops/data-entities/add-efficiency-in-quote-to-cash-concept`. This is the clearest primary-source evidence in this report for the owner's core question: **the two systems each have a real, separately-numbered sales-order-capable record; dual-write links them by reference (a synced copy + a cross-reference), it does not make Finance the sole owner of the sales order.**
- **documented — channels and where they land:**
  - **CRM opportunity** → D365 Sales Quote/Order (Dataverse-native, per Q2/above), optionally synced via dual-write into an F&SCM sales order for fulfillment/inventory/financial processing.
  - **Store/POS**: Commerce POS transactions are processed by the headless Commerce Scale Unit and integrate into F&SCM/Finance for financial statements — quote: "Dynamics 365 Finance offers an integrated experience for managing stores and e-commerce financial statements alongside the rest of their operations." Commerce also supports **"Customer orders in point of sale (POS)"** as a distinct object from a regular retail transaction: "Customer orders in POS allow retailers to capture sales where shoppers want to pick up products on a later date, pick up products from a different location, or have items shipped to them" (WebSearch summary of `learn.microsoft.com/en-us/dynamics365/commerce/customer-orders-overview`, **third-party**-summarized, not independently re-fetched verbatim).
  - **E-commerce**: same Commerce Scale Unit / storefront, same integration path into F&SCM.
  - **Free-text invoice with no order**: **owned entirely by D365 Finance**, explicitly bypassing the sales order: "A free text invoice isn't related to a sales order... You can't enter an item number on this kind of invoice... Free text invoices are used to sell a quantity of any kind of goods or services that are not in your inventory." URL: `https://learn.microsoft.com/en-us/dynamics365/finance/accounts-receivable/create-free-text-invoice-new` (procedure steps quoted verbatim; the summary framing sentence is third-party-derived).
  - **Sale of a fixed asset**: **documented, and confirmed to reuse the free-text invoice mechanism, not a standard sales order** — "This article explains how to dispose of a fixed asset using the free text invoice... Enter or select a value in the Fixed asset field. Select Post." URL: `https://learn.microsoft.com/en-us/dynamics365/finance/fixed-assets/tasks/dispose-fixed-asset-free-text-invoice`. Also: "For free text invoices, the fixed asset transaction type is always Disposal - sale" (WebSearch summary of `.../fixed-assets/enter-fixed-asset-transactions`, third-party-summarized). This is the single cleanest piece of evidence for the owner's "sale of company assets" scenario: **Finance owns it directly, through the same free-text-invoice document type used for any no-inventory sale, not through Sales/CRM and not through a standard sales order.**

### Q4. CRM: what it owns; creates or hands off?

- **documented** — D365 Sales (the CRM) owns Lead, Opportunity, Quote, Order, Invoice, Account, Contact, Competitor, Product — and, per Q3, can independently drive a deal through Quote → Order → Invoice **inside Dataverse** without ever touching Finance.
- **documented** — it also **hands off** to Finance/SCM for the operational/financial system of record via **dual-write**, which is explicitly bidirectional and near-real-time, not a one-way CRM-creates/Finance-consumes pipe: "Dual-write provides tightly coupled, bidirectional integration between finance and operations apps and Dataverse. Any data change in finance and operations apps causes writes to Dataverse, and any data change in Dataverse causes writes to finance and operations apps." URL: `https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/dual-write/dual-write-overview`. The quote-to-cash "Origin/Ownership" mechanism (Q3) shows this is genuinely bidirectional ownership, not CRM-always-wins: a quotation can originate and be owned by *either* system.
- This directly answers "what is the point of CRM if sales lives in Finance": **documented** evidence shows D365 Sales owns pre-sale relationship data (lead/opportunity/competitor tracking, activities, forecasting) that Finance has no model for at all, and can itself carry a deal to a Dataverse-native invoice — Finance is not a superset of CRM's data model, it is a parallel operational/financial system reconciled by dual-write.

### Q5. Projects: does Project Operations own records, or is it a view/dimension?

- **documented** — Project Operations **owns real Dataverse records**: Project, Project Task (WBS), Timesheet, and the summary/estimate/tracking data calculated from the WBS, per the "Saving changes to a project's work breakdown structure" doc (quoted in Q2). The WBS is edited through an embedded "Microsoft Project for the web" experience but saved back to Dataverse tables, with dedicated "Modified By," "Project for the web ModifiedBy/CreatedBy" columns proving these are first-class stored records, not a computed view: "If you check the Modified By column in the project tasks table, the table shows Microsoft Project as the user who made the most recent updates when a project task is edited."
- **NOT FOUND** — this session did not fetch pages proving how **Project Operations project cost/budget data reconciles into Finance's ledger for project billing** (e.g., dual-write mapping for project-to-cash); the d365-netsuite.md evidence file (prior research) separately confirmed a **D365 Finance-side** "project adjustment"/cost-recalculation mechanism (`https://learn.microsoft.com/en-us/dynamics365/project-operations/project-accounting/project-adjustments`) but that page sits under `project-operations/project-accounting`, suggesting Project Operations (not F&SCM) owns the project *transaction* ledger for time/expense, while GL posting/invoicing likely still flows to Finance — this specific hand-off was **not independently re-verified this session**, flagged **NOT FOUND**.
- Conclusion for the owner's "is Projects just a dashboard" question: **no** — both SAP PS and D365 Project Operations own genuine transactional master data (WBS/tasks/timesheets/budgets), confirmed by primary docs above; they are not read-only views over Sales/Finance data.

### Q6. Finance: what it owns — invoices/bills or only the ledger?

- **documented** — D365 Finance owns **both** a ledger (General ledger, vouchers) **and** first-class billing documents that don't derive from any order: the **free text invoice** is a Finance-owned, Finance-created document type, independent of Sales' Invoice entity and independent of a sales order (Q3 quote). It is not merely a ledger — it has its own header/lines, tax calculation, workflow states (Draft/Unrecoverable), and posting process.
- **NOT FOUND** — this session did not re-confirm from a primary page whether D365 Finance's standard (non-free-text) customer invoice, generated from a sales order, is a distinct table from the free text invoice or a shared "CustInvoiceJour" table with a type flag; that internal-schema-level claim is **inferred** from general F&SCM data-model knowledge, not verified via a fetched page this session.

### Q8. Contacts: shared master? Personal/private relationship management?

- **documented** — D365's cross-app contact model is the **Party** (Dataverse table `msdyn_party`) reconciled with F&SCM's **Global address book** (`DirPartyTable`), explicitly analogous to SAP's Business Partner: "The global address book is a centralized repository for master data that you must store for all internal and external persons and organizations that your company interacts with... You assign each party record to a party, and each party can be associated with one or more party roles in a company. Party roles include customer, prospect, worker, user, vendor, competitor, applicant, and contact." URL: `https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/organization-administration/overview-global-address-book`.
- **documented** — this is explicitly synced (not merged) with Dataverse's own **Account/Contact** tables via dual-write's Party concept: "The party is synced bi-directionally between the Dataverse party table and the Finance & Operations party (Global Address Book)... a party record will be generated automatically for each account and contact" (WebSearch summary of `dual-write/party-gab`, **third-party**-summarized, not independently re-fetched verbatim this session). So there are, architecturally, **two contact stores (Dataverse Account/Contact and F&SCM Global Address Book/DirPartyTable), reconciled by dual-write's Party abstraction** — directly parallel to SAP's CRM-Customer vs. SD-Customer vs. Business-Partner three-way reconciliation via CVI.
- **NOT FOUND** — no evidence of a "personal/private relationship management" layer distinct from the shared Account/Contact model was found in either product this session.
