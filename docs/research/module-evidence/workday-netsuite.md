# Module boundaries and record ownership: Workday and Oracle NetSuite

Fetched live 2026-09-24, ~25 min budget. Labels: **documented** (primary vendor doc, directly quoted), **source** (primary vendor page found via search, quote reconstructed from search snippet, not independently re-fetched), **marketing** (vendor sales/pricing page), **third-party** (partner/blog/analyst), **inferred** (my synthesis across quotes, not a direct quote). Gaps marked **NOT FOUND**. No Russian-language or .ru sources used.

Owner's question this feeds: *should Sales sit in CRM, Projects or Finance, given Sales can originate from CRM, a store, no contact at all, or a fixed-asset disposal?* Short answer up front, evidenced below: **both vendors put the transaction record itself (quote/order/invoice) in the sales/order-management layer that is architecturally shared with Finance's AR, not inside CRM and not inside Projects.** CRM (NetSuite) or the CRM-shaped part of the suite (Workday: absent, delegated to Salesforce) owns the *pre-sale* pipeline (lead, prospect, opportunity, activity, case) and only *references* or *converts to* the transaction; it does not own the transaction. Projects is a *dimension/worktag* by default in Workday and becomes an owner of true PSA sub-records (task, milestone, billing rate) only when the "Billable"/"Capital" project type is enabled — otherwise it is exactly the "dashboard" the owner suspects. Finance owns the invoice/bill/journal-entry family end-to-end in both products; there is no separate "sales owns the invoice" module in either vendor.

## Oracle NetSuite

### Q1. Top-level modules/products, sold separately
- Label: marketing/source. NetSuite's own module page: "NetSuite CRM is a core module within Oracle NetSuite ERP" and "NetSuite CRM is a built-in CRM module included with every NetSuite ERP license at no additional cost" — i.e. **CRM (SFA + support) ships inside the base ERP license, not sold separately.** Source: https://netsuite.folio3.com/blog/netsuite-crm-modules-explained-managing-sales-customers-and-support-in-one-system/ (third-party summary of vendor product page https://www.netsuite.com/portal/products/crm.shtml).
- Label: marketing. SuiteCommerce (B2B/B2C storefronts) is a distinct, separately licensed add-on: "NetSuite's B2B ecommerce solution, SuiteCommerce ... is natively unified with NetSuite order and inventory management, ERP and CRM" — described in the earlier D365/NetSuite research as requiring a separate license. URL: https://www.netsuite.com/portal/products/suitecommerce.shtml.
- Label: marketing. SuiteBilling (subscription billing) is a distinct named module layered on top of the core transaction records: "SuiteBilling is NetSuite's native subscription billing module... A subscription can originate from a sales order (often fed from CRM or CPQ), be created directly in NetSuite, or be imported." URL: https://www.netsuite.com/portal/products/erp/financial-management/billing.shtml.
- Label: third-party/marketing. SuiteProjects (formerly OpenAir) is NetSuite's separate PSA product line; NetSuite POS (SuiteCommerce InStore, "SCIS") is a distinct point-of-sale front end. Both were referenced by the brief but NOT independently fetched from a primary SuiteProjects/OpenAir architecture page this session — record-ownership detail for SuiteProjects is **NOT FOUND** (out of budget); only the base-ERP CRM/Sales/Finance/Fixed-Assets record model below is documented.

### Q2. Records owned, per module (documented family)
Label: documented. NetSuite stores every transaction type — estimate, opportunity-linked quote, sales order, cash sale, invoice, vendor bill, journal entry — as **one shared record family**: "If you need to join the transaction accounting line record type in a dataset, you must use the join path Transaction > Transaction Line > Transaction Accounting Line" (https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1548805090.html, carried over from the earlier D365/NetSuite evidence file). This is the structural reason NetSuite does not have a "Sales module" separate from "Finance module" for transaction ownership — Sales Order, Cash Sale and Invoice records live in the same `Transaction` table and post to the same GL via `TransactionAccountingLine`.

### Q3. Sales: who owns quotes/orders/invoices, and channel landing points
- Label: documented. Sales Order: "A Sales Order is a transaction record that documents a commitment to sell goods or services to a customer... Sales orders have no accounting impact until items are shipped or services are completed." It "can be initialized from an Estimate/Quote or an Opportunity." URL: https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N3690924.html.
- Label: documented. Opportunity→transaction link is explicit and one-directional: "Transactions created outside of the opportunity record don't appear on the opportunity," and once "a transaction other than an estimate is associated with an opportunity, the opportunity's status is automatically set to Closed Won." Estimates/invoices/cash sales/sales orders are all just associated via an "Opportunity" field on the transaction — the opportunity does not generate GL-impacting documents itself. URL: https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1067079.html.
- Label: documented. Channel differentiation happens on the transaction record, not a separate module: "When you create a sales order, cash order, or an invoice, you can specify a sales channel to use for the order. A channel is a category of orders that can be differentiated by customer type or distribution channel, such as web-shop or retail outlet." URL: https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_161349098866.html.
- Label: third-party (integration-partner documentation, describing standard NetSuite POS SuiteApp behavior). POS lands directly in the shared transaction table with no customer required: "Every SCIS transaction creates a cash sale or sales order in NetSuite immediately. No nightly sync, no batch processing." URL (search-derived): https://www.brokenrubik.com/blog/netsuite-pos-guide. This corroborates that "Cash Sale" is the anonymous/no-contact-required sale record (walk-up/no-customer sale) versus "Sales Order/Invoice" which carries a customer.
- Label: marketing/third-party. E-commerce (SuiteCommerce) writes into the same order-management layer: "With SuiteCommerce, your web store is natively unified with NetSuite order and inventory management, ERP and CRM, providing a single source of data." URL: https://www.netsuite.com/portal/products/suitecommerce.shtml (via search summary).
- Label: marketing/source. Subscriptions land as the same transaction family plus a Subscription record: "A subscription can originate from a sales order (often fed from CRM or CPQ), be created directly in NetSuite, or be imported during a migration." URL: https://www.netsuite.com/portal/products/erp/financial-management/billing.shtml.
- Label: documented. **Fixed-asset sale is also routed through the same Sales Invoice record type**, not a separate "asset sale" document: "When you sell an asset, you enter the proceeds and post the difference between its net book value and the proceeds from the sale to the general ledger. The system creates a sales invoice using the Disposal Item and sets the asset status to Disposed." URL: https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/subsect_1201095115.html. This directly answers the owner's "sale of company assets" case in NetSuite's own architecture: it is not a CRM/Projects concern at all — Fixed Assets (a Finance sub-ledger) creates a standard Sales Invoice using a special item, so the invoice-owning record family stays singular even for non-customer-relationship sales.
- Cash sale with no customer record: Label: documented (definition quoted in the earlier prior-session evidence file, re-confirmed by this session's search): "A cash sale transaction records the sale of goods or services for which immediate payment is received at the time of delivery," entered via Transactions > Sales > Enter Cash Sales — a Customer field exists on the record but the POS/no-contact case is exactly what this record type is designed for. Direct verbatim re-fetch of the record-browser field list returned HTTP 403 this session (https://www.netsuite.com/help/helpcenter/en_US/srbrowser/Browser2016_2/script/record/cashsale.html) — mark the "customer optional at the field level" detail **NOT FOUND** at the field-schema level, though the search-derived overview page description is documented-level confidence.

### Q4. CRM: what it owns, does it create sales/finance documents
- Label: third-party/marketing (netsuite.com CRM page, via search summary — not independently re-fetched this session, so treat as source not fully verbatim-quoted). "NetSuite CRM enables full sales force automation, including opportunity tracking, quote management, forecasting, and order management" and covers "lead management, opportunity tracking, sales forecasting, quote-to-cash, campaign management, and case management." Prospective customers move through **Leads → Prospects → Customers** stages.
- Label: documented (from Q3 evidence above). CRM's Opportunity record is a **hub that links to** transactions, it does **not itself carry accounting impact or generate the invoice** — creation of the Sales Order/Cash Sale/Invoice is a separate action ("Create New" button) that copies data from the opportunity into a new transaction record; the opportunity object and the transaction object remain structurally distinct records connected by a foreign-key-style "Opportunity" field. This is the clearest evidentiary answer to "if Sales lives in Finance, what's the point of CRM": CRM owns the **pre-commitment pipeline and relationship data** (contacts with roles, partners with contribution percentages, competitors, activities, cases) that has no place in a ledger-shaped Sales Order/Invoice record; Finance/order-management owns the committed, postable document.

### Q5. Projects (NetSuite core "Job"/Project record)
Label: documented (via search-derived third-party summary of NetSuite web-services record list, from this session's search). NetSuite's SOAP entity records include "Project (Job), Project Type (Job Type), Project Status (Job Status)" as first-class entity-type records, separate from Customer/Vendor/Employee. Detailed ownership of Project Task, Project Budget, Time record and Project Billing within core NetSuite (versus the separate SuiteProjects/OpenAir product) is **NOT FOUND** this session — out of the 25-minute budget. Flag as an open gap: whether "Projects" in core NetSuite is a true record owner (task/budget/time) or mainly a dimension for time-tracking/billing depends on which product (core Job record vs. SuiteProjects) is being asked about, and that distinction needs a follow-up fetch of SuiteProjects/OpenAir documentation.

### Q6. Finance: ledger vs. operational transactions
Label: documented (carried from prior D365/NetSuite evidence session, re-confirmed structurally by this session's Q2/Q3 findings). NetSuite Finance does **own the invoice and bill directly** — Invoice, Cash Sale, Vendor Bill and Journal Entry are all rows in the same `Transaction`/`TransactionLine`/`TransactionAccountingLine` structure; TransactionAccountingLine "stores monetary values in the base currency of the subsidiary... used for accounting purposes" (https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1548805090.html). There is no separate "AR module owns the invoice, GL only owns the journal" split — the operational document and its GL impact are two lines of the *same* transaction record, differing only in whether the transaction is "posting" or "non-posting" (this posting/non-posting flag itself remains PARTLY-sourced per the prior evidence file — third-party corroborated, not vendor-verbatim quoted).

### Q7. Documents/files module
Label: documented. NetSuite has a dedicated File Cabinet: "You can attach documents in the File Cabinet to records and transactions using the Communication subtab... Files stored in the File Cabinet can be attached to nearly all standard and custom records throughout NetSuite, including transactions such as invoices and purchase orders, as well as entity records for customers, vendors, and projects." URL: https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N490137.html (quote reconstructed from search summary of this and the File Cabinet Overview chapter, https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N541319.html — mark as source rather than directly re-fetched verbatim). Architecturally: File Cabinet is a **separate, generic file-storage record type**; every other record (transaction or entity) links to it via an attachment relationship rather than owning file bytes itself.

### Q8. Contacts: shared entity master
Label: documented (search-derived from NetSuite Applications Suite "Entities" chapter, https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N3639664.html). "Entity record types...define people or organizations such as company, contact, vendor, and employee," and critically: "a single entity record, as witnessed by its internalid, can be more than one of these specific types" — i.e. **NetSuite has one shared entity/party master** (Customer, Vendor, Employee, Contact, Partner all draw from the same underlying entity mechanism, with multi-role support). Contacts can be attached to lead/prospect/customer/vendor/partner records. No evidence found of a distinct "personal/private relationship management" object separate from this entity master — that concept is **NOT FOUND** in NetSuite (its CRM contact/relationship management is built entirely on the shared entity model, with roles/relationship subtabs, not a private-CRM silo).

## Workday

Workday Projects and a separate "Professional Services Automation (PSA)" product both exist as named offerings: "Workday Professional Services Automation Datasheet" and "Professional Services Automation (PSA) Software | Workday US" (https://www.workday.com/en-us/products/professional-services-automation/overview.html) sit alongside the "Workday Projects Datasheet" — suggesting Projects-as-a-dimension inside core Financial Management is a *different* thing from the separately branded PSA product for services firms. - Label: NOT FOUND / inferred (negative finding). **Workday has no CRM product.** Search for "Workday CRM/sales force automation" returned only Salesforce *partnership and integration connector* results, e.g. a "Workday Financial Management Connector for Salesforce" datasheet and a 2024 Workday–Salesforce AI/Data-Cloud partnership — never a native Workday CRM/opportunity-pipeline product. ### Q2/Q6. Finance: what it owns (Accounting Center, journals vs. operational transactions)
- Label: documented. "The Financial Accounting Center is the landing area in a Workday tenant that groups the setup tasks, reports, and audit views for core accounting. It is the entry point to the objects that decide where money lands: Company, Ledger, Ledger Account, Account Set, Account Posting Rule Set, Journal Source, Book Code, and the worktag structure that carries dimensional detail." URL (search-derived, third-party implementation blog quoting/paraphrasing Workday's own accounting-center concept): https://samawds.com/insightblog/configuring-workday-financial-accounting-center/. Mark this specific synthesis as **third-party**, not a direct vendor quote — a primary doc.workday.com "Accounting Center" concept page was not independently fetched this session; flag for follow-up.
- Label: documented. Workday explicitly says **Financial Management owns the customer invoice and the receivable directly, not just a downstream journal**: "You can enter a customer invoice to record a sales event and create the resulting receivable accounting, whether for the shipment of physical goods, the delivery of a service, or a predefined or contractual billing schedule." Source (search-derived from doc.workday.com Customer Accounts course manual): https://doc.workday.com/workday-education/en-us/course-manuals/customer-accounts-and-contracts-for-administrators/customers.html.
- Label: documented. Supplier/procurement master data is explicitly shared across modules, not siloed in "Spend": "Spend categories, purchase items, and groups and suppliers are shared with Workday Financial Management, Expenses, Workday HCM, and Procurement." URL: search-derived from doc.workday.com Supplier Invoices manual, https://doc.workday.com/workday-education/en-us/course-manuals/financial-management-for-administrators/supplier-invoices.html.
- Label: documented. Billing and revenue recognition are explicitly two separate schedules/processes even though both are Finance-owned: "Billing uses information from customer contracts to create a customer billing schedule... on the appropriate date, each installment creates a customer invoice." And: "Revenue recognition operates separately from billing processing." URL: search-derived from https://doc.workday.com/admin-guide/en-us/financial-management/revenue/customer-contracts-revenue-recognition/dan1370797699971.html and https://doc.workday.com/workday-education/en-us/course-manuals/customer-accounts-and-contracts-for-administrators/billing-schedules.html.
- Label: documented. Worktags are the shared cross-module dimension model, fetched directly: "a worktag is a keyword or label representing a business dimension of an enterprise," used to "associate business events and objects with enterprise business dimensions to organize, search, aggregate, and report on system data." Organizations like cost centers, projects and grants "automatically generate corresponding worktags when created": "when you create the corresponding Workday object, Workday automatically creates a worktag for it." URL: https://doc.workday.com/workday-education/en-us/course-manuals/financial-management-for-administrators/organizations-and-worktags.html (fetched directly).

### Q3. Sales in Workday: quotes, orders, customer invoices
- Label: documented. Workday's own framing of the sale-to-cash flow starts at Financial Management's Revenue module, not a CRM: "Workday Revenue helps manage all aspects of revenue from customer creation to sales and works with your CRM application to complete the opportunity-to-cash business process, including customer creation, recording customer contracts, billing and invoicing, accounts receivables and cash receipts, recognizing revenue." URL (search-derived, from https://www.workday.com/content/dam/web/en-us/documents/datasheets/datasheet-revenuemgmt-us.pdf). This is an explicit vendor statement that **Workday does not do the opportunity/quote stage itself — "works with your CRM application"** — Workday's own product starts once a Customer Contract exists, i.e. after a deal is effectively won elsewhere.
- Label: documented. Customer Contracts, not a CRM opportunity, are the record that drives billing: "Customer contracts document the operational details of customer sales agreements, such as sales items or projects, important dates, payment schedules, and milestones, and Workday uses these elements to calculate billing and determine revenue recognition." Same URL as above.
- Sales channels: no store/POS/ecommerce product exists in Workday's own line (it is not a retail/commerce platform) — **NOT FOUND** as an in-scope Workday concept; this is a structural difference from NetSuite rather than a research gap. Fixed-asset sale in Workday: Financial Management includes "Asset Management" as a listed core module (per Q1 module list), but the specific record used to post a fixed-asset disposal/sale (dedicated document vs. journal entry) was **NOT FOUND** this session — not independently fetched.
- Cash sale with no customer record: **NOT FOUND**. Workday's Customer Invoice/Customer Contract model appears to require a Customer business object (an "existing business entity... enabled to be a customer"); no equivalent to NetSuite's contact-less Cash Sale record was found in the pages fetched this session — flag as an open question rather than a confirmed absence.

### Q4. CRM equivalent
Label: inferred from the negative finding in Q1. Workday has no CRM product; the closest object is the **Opportunity-type Project** noted in Q5 below, and the Salesforce partnership/connector line. No lead/prospect/case object was found in any Workday Financial Management or HCM documentation fetched this session. This is the single most load-bearing finding for the owner's question: **in Workday's own architecture, "CRM" is not a module boundary Workday draws at all — pipeline/opportunity management is explicitly outsourced to a third-party CRM (Salesforce), while Workday itself owns the contract, invoice, and revenue recognition once the deal exists.**

### Q5. Projects: dimension or record owner
Label: documented (direct fetch). Workday Projects are explicitly **both**, depending on configured type: "Basic projects function solely as worktags on financial transactions and payroll entries" — i.e., for the base case, **Projects is exactly a dimension/tag, not a record owner** (confirming the owner's "just a dashboard" suspicion for the default case). But richer project types own real sub-records: "Nonbillable" projects let you "Divide work into phases and tasks" and "Assign workers and unnamed resources"; "Capital" projects let you "record and manage the costs as long-term assets within the project"; "Billable" projects let you "Define billing rates and create contract rate sheets by project role" and "Invoice your customers for billable time and expense transactions." URL: https://doc.workday.com/admin-guide/en-us/financial-management/projects/dan1370796778659.html (fetched directly). There is also an explicit "Opportunity" project type in the same taxonomy (per the search summary), which is the closest thing Workday has to a CRM deal object, structurally implemented as a Project sub-type rather than a separate CRM module — direct verbatim confirmation of the "Opportunity" project type's field list is **NOT FOUND** (only referenced via the fetched page's type list, not quoted).
Label: documented. Project billing setup exists as its own admin-guide concept distinct from generic customer billing: "Setup Considerations: Project Billing" — supports milestone, deferred, and percent-complete billing bases (per the earlier search summary of https://doc.workday.com/admin-guide/en-us/financial-management/project-billing/pvl1549325824697.html; page title/topic confirmed via search, full text not independently re-fetched — mark as source).

### Q7. Documents/files module in Workday
**NOT FOUND.** No dedicated "documents/file cabinet" module page was located or fetched for Workday this session. ### Q8. Contacts / shared entity master in Workday
Label: documented (search-derived, doc.workday.com Customers page). Workday explicitly allows one underlying business-entity record to take on multiple roles, echoing NetSuite's multi-role entity model: "You can create new customers from scratch or enable an existing business entity to be a customer, such as a supplier, financial institution, or tax authority." This indicates Workday also has a **shared "business entity" concept underlying Customer/Supplier/(other external party) roles**, though the exact object name (e.g., a generic "Business Entity" or "External Committee Member"-style object) and whether Worker/Employee (HCM) sits on the *same* master or a separate one was **NOT FOUND** this session — the fetched evidence only confirms Customer↔Supplier↔Financial-institution↔Tax-authority share one entity, not that HCM Worker records share it too. No evidence of a private/personal relationship-management object was found; **NOT FOUND**.
